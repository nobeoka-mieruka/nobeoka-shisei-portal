# 新機能ロードマップ A〜M：実装可能性の4段階評価（設計ドキュメント）

> 2026-08-24作成。「市民が課題→質問→答弁→政策→予算→議案→事業→結果まで追える」ための
> 12機能案（A〜M）について、依頼どおり**実装前の設計確認**として、既存データ・型定義・
> ルート構成をもとに4段階（1: 既存データで実装可能／2: 軽微な追加で実装可能／
> 3: 大規模な追加調査が必要／4: 現状では困難）に分類する。今回のセッションでは
> このドキュメントの作成のみを行い、大規模な新規実装は行わない（依頼の「上記を一気に
> 実装しないでください」に従う）。

## 分類結果一覧

| # | 機能 | 分類 | 理由（要約） |
|---|---|---|---|
| A | 一般質問「その後」追跡 | **3** | `generalQuestions.json`/`councilSpeechSummaries.json`に「関連議案ID」「関連予算」フィールドが無い。AI関連候補と確認済み関連付けを区別する新フィールド設計が必要。まずは高確度な少数事例（同一会期・同一テーマの議案）から手動で試験登録する運用が現実的 |
| B | 議案ライフサイクル | **2** | `billVotes.json`には既に`委員会付託`情報・採決日等があり、`CouncilSessionDetailPage`等で会期単位のタイムライン表示は既存。「提出」「委員会審査」の詳細ステップ表示は既存フィールドの組み替えでUI実装できる可能性が高い。ただし全議案の審査経過が一次資料で追えるとは限らない点に注意 |
| C | 年度別「延岡市政カルテ」（`/years/:year`） | **2** | `archiveFiscalYears.json`（財政）・`archiveMayorTerms.json`（市長）・`civicTimelineEvents.json`（年表）・`generalQuestions.json`（一般質問、年度フィールドあり）・`electionResults.json`（選挙）は全て年度でフィルタ可能な既存データ。新規ルート＋既存データの集約ページとして実装可能性は比較的高い。ただし「主要政策」の年度別紐付けは未整備（Aと同じ課題） |
| D | テーマ横断ページ | **2** | `councilSpeechSummaries.json`の`topics`フィールド（既存の語彙タグ）を土台にできる。ただし「関連議案」「関連予算」「関連政策」への横断はA・Cと同じ関連付けデータが必要なため、質問・答弁の横断表示までは2、議案・予算まで含めた完全横断は3相当 |
| E | 「延岡市のいま」簡易ダッシュボード | **1** | 人口・市債残高・基金残高・財政指標・市長・市議会議員数はすべて既存データ（`archiveFiscalYears.json`等）から直接取得可能。既存の`calculateGeneralQuestionStats`等と同様の「単一集計モジュール」を財政向けに1つ追加すれば実装できる |
| F | 長期推移（前年比・5年前比・10年前比） | **2** | `archiveFiscalYears.json`は年度キーで格納済みのため、前年・5年前・10年前のレコードを取得して差分計算する関数は追加実装で対応可能。「定義変更の注記」は`definitionNote`フィールドが既に一部存在するため活用できるが、全指標分の注記整備はやや手間がかかる |
| G | 未解明データ一覧（`/research-gaps`） | **1** | `reports/phase33-master-unresolved-ledger.json`（UNR台帳、現在31件）が既にこの機能の内部データそのものである。市民向け表示用に必要なフィールド（対象／分かっていること／不足情報／確認済み資料／次の調査候補）も台帳のスキーマに既に存在する。**既存データをそのままページ化するだけで実装できる、最も費用対効果が高い項目** |
| H | データ訂正履歴 | **2** | 通常の`updateHistory.json`と別スキーマ（訂正日／対象データ／訂正前／訂正後／訂正理由／根拠資料）を新設する必要があるが、型定義・生成スクリプトの追加のみで対応可能。今回のセッション自体で発生した多数の訂正（市長代数の訂正等）を初期データとして投入できる |
| I | 出典証拠カード | **1〜2** | 多くのデータファイルに`sourceRefs`（title/url/organization/accessedAt等）が既に構造化されているため、既存詳細ページに「出典を見る」の共通UIコンポーネントを追加すれば1に近い。ただし全ファイルで`sourceRefs`のフィールド名・粒度が統一されていない（Phase79の出典網羅率監査で確認済み）ため、全面展開は2 |
| J | オープンデータ（CSV/JSON配布） | **2** | `src/data/*.json`は既にビルド成果物に含まれる静的ファイルであり、個人情報を含まないものを`/opendata/`配下等へそのまま複製配布することは技術的に容易。利用条件・著作権表記（原資料の転載可否）の整理が必要なため、法的確認込みで2 |
| K | 「市政の流れ」統合データモデル | **4** | A・B・Dの全関連付けが揃って初めて意味を持つ最終形。既存データの再利用だけでは到達できず、市民課題→質問→答弁→政策→予算→議案→採決→事業→結果の全リンクを人手で確認しながら育てる長期プロジェクトになる。現時点では時期尚早 |

## 推奨する着手順（効果が高く、既存データを再利用できるものから）

1. **G（未解明データ一覧）**：既存のUNR台帳をほぼそのまま公開ページ化できる。実装コストが
   最も低く、CLAUDE.mdの「確認できない情報を確認中等で区別する」方針とも直接合致する。
2. **E（延岡市のいま）**：既存データの再集約のみ。
3. **I（出典証拠カード）**：まず主要4カテゴリ（財政・選挙・市長・一般質問）に絞って共通
   コンポーネント化する。
4. **C（年度別カルテ）**：既存データの年度フィルタ集約。
5. **B・F**：既存データの組み替え・差分計算。
6. **A・D・H・J**：追加スキーマ設計を伴うため、G〜Fが安定してから着手する。
7. **K**：当面着手しない。

**今回のセッションでは、上記のいずれについても実際のルート・コンポーネント実装は
行っていない**（依頼の「まず設計確認」「一気に実装しない」という明示的な指示に従い、
分類のみを行った）。次フェーズで着手する場合は、まずGから小さく始めることを推奨する。
